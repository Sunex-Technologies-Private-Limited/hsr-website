## 1. Critical blockers — fix before taking real money

These are not polish. They can leak products, leak customer data, or mark unpaid orders as complete.

### 1. Anyone can run the admin API
`adminProcedure` exists, but **admin product mutations are public**.

```25:48:server/routes/admin.ts
export const adminRouter = router({
  createProduct: publicProcedure.input(productSchema).mutation(...)
  updateProduct: publicProcedure.input(productSchema).mutation(...)
  deleteProduct: publicProcedure.input(productSchema).mutation(...)
```

`/admin` has **no login gate**. Anyone who finds the URL can add, edit, or delete catalog items. Upload is role-checked; tRPC admin is not.

**Fix:** wrap every admin mutation in `adminProcedure`, hide `/admin` behind role check, add CSRF + audit log.

### 2. Payment is not actually verified
Checkout uses a **hardcoded test key** `rzp_test_mock`. On Razorpay “success” it **clears the cart and shows the confirmation page** without verifying signature, capturing payment, or waiting for webhook.

```41:50:client/src/pages/Checkout.tsx
key: "rzp_test_mock",
handler: function (response: any) {
  clear();
  setLocation(`/order-confirmation/${data.orderId}`);
},
```

Order is created as `pending`. Confirmation still shows **Download** immediately.

Webhook is worse: if `x-razorpay-signature` is **missing, it still processes the event**. Signature is computed on `JSON.stringify(req.body)` — Razorpay needs the **raw body**. So even a real webhook will fail or be forgeable.

**Fix:**
- Live Razorpay keys from env only
- Verify `razorpay_payment_id` + `razorpay_signature` on the server before marking paid
- Serve downloads only when `status === "paid"`
- Capture raw body for webhook HMAC
- Reject unsigned webhooks

### 3. Anyone can read any order
`orders.getById` is public. Confirmation URL is `/order-confirmation/123`. Guess IDs, get names, emails, download paths.

**Fix:** secret token in the URL, or require the purchaser session/email + HMAC.

### 4. Downloads are not secure
`/api/downloads/:slug` checks “did this email ever have a paid order containing this slug?”, then N+1 queries every order. If the file is missing it returns a **plain-text mock file**. Guest checkout users may never get a session, so they cannot download after leaving the confirmation page.

**Fix:** signed, time-limited tokens (S3 presign already exists). Store `downloadToken` on `orderItems`. Don’t match only by email.

### 5. SQLite as the production database
Docs say MySQL. Code is `better-sqlite3` + local `sqlite.db`. Fine for a prototype. For payments, users, and files it will corrupt under concurrent writes and cannot be shared across servers.

**Fix:** Postgres (or real MySQL) with foreign keys, indexes, and transactions around order creation.

### 6. Cookie + CORS setup is unsafe
- `cors()` with no origin allowlist
- Helmet CSP turned off
- Session cookie `sameSite: "none"` (cross-site cookies)
- Login/register throw generic `Error` instead of `TRPCError`

Together this is a CSRF / session-leak surface.
